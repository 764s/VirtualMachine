为这个大纲的第二部, 推荐脚本形式. 你需要考虑现代语言的优化方向, 还有实际使用目的, 给出备选方案, 并解释各自的优缺点.

FFEditor 胶水执行器与技能虚拟机架构总纲
(1) 原始背景与核心痛点 (The Context)
项目环境： 致力于开发一款 2D 横版动作游戏，并依托于自研的、类似 Unity 的 ECS 架构游戏引擎编辑器（FFEditor）。
业务场景： 需要为复杂的战斗系统（包括技能流转、状态效果、子弹行为、AI 等）提供一个统一的底层逻辑执行架构。
核心痛点（过往尝试的局限）：
传统行为树严重依赖宿主语言的调用栈，并需要维护恼人的 Running 状态，极难进行状态快照。
效果器模式、事件驱动模式和任务组件模式，要么牺牲了树状嵌套结构，要么导致逻辑碎片化，要么需要手写大量状态机样板代码。
架构终极目标： 打造一个“偏瞬态”的胶水执行器。在保持底层完全控制、规避宿主语言栈特性的同时，兼顾脚本语言的灵活性与更友好的结构化，并始终坚持极其严格的实例与静态数据分离原则。
(2) 语言形式与 UI 映射 (The Format & UI Duality)
形态定位： 提供脚本与可视化 UI 的双向互通支持，但以脚本为唯一真理之源 (Source of Truth)。
物理隔离： 为了确保脚本能完美、无乱线地生成 UI 图，在语法上强制将逻辑一分为二：
流程脚本 ([Flow])： 负责宏观时间轴。仅允许使用挂起、系统函数调用和受限的分支/循环。它会被 FFEditor 解析并渲染为一张整洁的有向无环图 (DAG) 般的 UI 节点连线，主要用于直观调试与骨架搭建。
逻辑脚本 ([Logic])： 负责微观数据流。允许复杂的局部计算和短路逻辑，但严禁任何挂起指令。它在可视化 UI 中退化为一个不可展开的“纯脚本黑盒节点”，彻底消灭了图形化表达复杂数学公式的痛点。
(3) 语言特性需求 (Language Features)
结构降维： 脚本语法层面上支持自定义类型（最低限度支持结构体）。但在底层，所有结构体会被拍扁映射为连续的寄存器槽位，运行时不存在对象实例。
原生异步： 支持原生的挂起语法（如 wait）。虚拟机遇到此指令直接保存状态并让出执行权，天然消除传统的 Running 枚举。
函数互调与覆盖： 支持脚本间的函数调用与返回值获取。允许使用纯脚本逻辑通过统一的系统调用表 (Syscall Table) 热覆盖或替换宿主语言（C#）的既有缺陷函数。
(4) 性能与网络同步能力 (Performance & Netcode Capabilities)
执行效率： 宿主语言 (C#) + 自定义虚拟机执行的综合性能，必须大于或等于纯 Lua 实现的封闭逻辑。
零分配与极速快照 (Zero GC & Instant Rollback)： * 采用“静态指令流 (Bytecode) + 预分配实例内存 (Registers)”的设计。战斗中严禁任何运行时的内存分配。
天然支持帧同步回滚： 虚拟机的全部状态被压缩为纯粹的连续值类型数据（IP, WaitFrames, Registers[]）。这使得游戏引擎在进行预测回滚 (Prediction & Rollback) 时，状态快照的保存与恢复仅需执行极低开销的内存拷贝 (Memcpy)，彻底免除传统面向对象架构中深拷贝复杂对象树带来的海量性能开销。
(5) 语言演进与扩展性 (Language Evolution & Extensibility)
语法设计的兼容性： 放弃自造的小众符号，采用类似 C# Attribute（特性）的标记法（如 [Flow] 和 [Logic]）来区分脚本块。
无缝切换语言： 这种标准化的前缀设计，使得未来可以极度方便地切换脚本形式，甚至直接使用已有的主流语言（例如直接写 C# 代码配合 Roslyn 分析器，或者使用 Lua 配合宏注释）。只要抽象语法树 (AST) 的标准不变，前端语言层可以随时拔插替换。
(6) 实施推进路线图 (Implementation Pipeline)
为了保证底层稳固与逻辑自洽，工程实施将严格遵循以下五步走策略：
设计脚本形式 (Script Design & Vision)：
明确领域特定语言 (DSL) 的样貌。规划好变量声明、[Flow] 和 [Logic] 的语法边界、异步挂起语句及函数调用格式。给出一个“写起来极其舒服”的预期，并为后续的词法分析与 AST 结构定义提供基准依据。
手写 AST 验证执行 (Manual AST & Interpreter)：
跳过字符串解析。在 C# 中手动实例化一棵包含循环、分支和挂起的 AST 节点树。利用 C# 协程 (IEnumerator) 编写一个树走式解释器 (Tree-Walking Interpreter)，快速跑通并验证业务逻辑与控制流模型的正确性。
脚本转 AST 验证执行 (Parser Integration)：
编写词法分析器 (Lexer) 和语法分析器 (Parser)。将第一步设计的纯文本脚本，成功解析并转化为第二步验证过的 AST 树，再次放入解释器执行。这标志着前端文本到逻辑模型的通道正式打通。
设计虚拟机与快照机制 (VM & Snapshot Design)：
抛弃协程解释器。设计极其紧凑的底层指令集 (Bytecode OpCodes) 和一个无栈帧、依靠指令指针 (IP) 轮询的“偏瞬态”寄存器虚拟机。在此阶段同步实现基于值类型拷贝的快照 (SaveState) 与回滚 (LoadState) 接口。
脚本转 AST 转字节码执行 (Full Compilation Pipeline)：
编写编译器 (Compiler)，遍历 AST，完成跳转偏移量的回填 (Backpatching) 和静态寄存器分配。将 AST 拍扁为一维字节码数组，送入第四步设计的虚拟机中执行。这标志着高性能底层架构的最终闭环。

(7) 对既有三套旧方案的人工压缩回顾

这一部分不是为了否定旧方案，而是为了把它们已经验证过的优点、已经暴露出的痛点，以及它们之间共享的底层思路，压缩成后续脚本设计的直接依据。

一个非常重要的前提是：
这三套东西并不是彼此孤立的三种世界观，而是同一套战斗框架在三个不同业务面的自然演化：
- 技能系统，负责“角色主动释放的主流程”；
- 子弹系统，负责“脱离角色后仍要持续运行的实体行为”；
- 状态效果系统，负责“跨帧、跨事件、跨来源的附着式逻辑”；
- 子弹和状态效果都没有完全另起炉灶，而是部分复用了技能效果器的能力，只是又各自叠加了自己的调度与生命周期约束。

因此，新 VM / 胶水执行器的目标，不应该是简单替换某一个系统，而是把这三类东西已经分散实现的“流程控制、生命周期管理、状态隔离、目标选择、效果执行、事件驱动、可视化表达”抽成一套更统一的底层模型。

(7.1) 旧方案一：技能系统 (Skill / SubSkill / EffectProcessor)

这是当前最接近“主流程脚本”的一套实现。它承担的是角色战斗中最核心的那条时间线：输入判定、技能切换、技能开始、技能持续执行、子技能生效、技能结束/打断。

### 1. 核心对象关系

可以把这一套系统压缩成下面这条链：

`SkillBehaviour -> Skill -> SubSkill -> SubskillEffectProcessor -> EffectProcessor`

其中：
- `SkillBehaviour` 是角色技能系统的总控制器，负责管理技能列表、当前运行技能、切换规则、默认技能、强制技能、忽略目标缓存等。
- `Skill` 是某一个技能实例，绑定具体的 `ISkillAsset`，负责开始条件、结束条件、子技能列表、技能结束效果器等。
- `SubSkill` 是技能内真正持续每帧执行的“效果生效体”，通常一个技能有多个子技能。
- `SubskillEffectProcessor` 是子技能的单个效果器，内部又分成条件、数据效果、视觉效果三段。
- `EffectProcessor` 是真正执行“条件检查 -> 目标生成 -> 数据效果 -> 视觉效果”的底层通用执行器。

这说明当前技能系统已经天然分成了两层：
- 外层是“技能流程调度”；
- 内层是“效果器执行流水线”。

这对新方案非常重要，因为它证明了：
**战斗主流程和局部效果结算，本来就是两种不同粒度的逻辑。**

---

### 2. 构建过程

#### 2.1 SkillBehaviour 的构建

`SkillBehaviour` 在构造时，会遍历配置里的 `SkillAssets`，为每个资源创建一个 `Skill` 实例，并建立 `skillDic` 便于按技能 ID 查找。

也就是说，当前技能系统在“角色初始化时”已经把：
- 技能资源；
- 技能运行对象；
- 目标忽略缓存；
全部准备好。

这是一种非常典型的“静态资源 + 运行时实例”分离思路。

#### 2.2 Skill 的构建

每个 `Skill` 在构造时会做几件关键的事情：

1. 根据 `skillAsset.ConditionGroups` 创建一组 `ConditionTrigger`。
   - 这部分负责技能启动条件的组合判断。
   - 例如是否着地、距离、输入、受击状态、程序标记等。

2. 根据资源创建 `StartCondition` 与 `CompleteCondition`。
   - 这是技能开始/结束层面的附加条件。

3. 从 `SkillEffectProcessorPackageUtil.GetOrCreate(skillAsset)` 获取或创建技能对应的效果器包。
   - 这是技能静态部分的缓存。
   - 内部可能包含：技能结束效果器、各个子技能的效果器数组。

4. 如果技能有 `SubSkillAssets`，就逐个拿到对应的 `SubskillEffectProcessor[]`，再构造 `SubSkill`。
   - 一个技能最终运行时真正逐帧执行的是 `SubSkill`。
   - `Skill` 自己更像“流程壳”和“入口管理器”。

#### 2.3 子技能效果器的构建

子技能效果器的构建过程，是当前战斗逻辑里最有代表性的部分：

1. `SubSkillEffectProcessorUtil.Create(...)`
2. `ConditionUtil.CreateCondition(...)`
3. `DataEffectUtil.CreateDataEffect(subSkillAsset)`
4. `SkillVisualEffectBuilder.CreateTasks(subSkillAsset)`
5. 拼成 `SubskillEffectProcessor`

具体来说：
- 条件部分会被拆成：
  - 普通条件 (`INormalCondition`)
  - 加潜在目标 (`IAddPotentialTarget`)
  - 检查潜在目标 (`ICheckPotentialTarget`)
- 然后由 `EffectProcessorConditionCollector` 重新组装成一个最终的 `ConditionAnd<EffectContext>`。
- 数据效果会生成 `IDataEffect[]`，内部既包含默认伤害/能量/治疗等，也会叠加资源里定义的附加数据效果。
- 视觉效果会被组织成 `VisualEffectDefault`，内部还是一个条件任务树，但运行上下文换成了 `VisualEffectContext`。

这说明当前系统已经有一个非常稳定的事实：

> 一个“技能生效点”并不是单条指令，而是一个标准的三段流水：
> 条件 -> 目标 -> 数据效果 / 表现效果。

这个事实在新 VM 里非常值得保留，因为它已经高度贴合战斗业务。

---

### 3. 业务举例

#### 例子 A：技能开始条件

当前技能开始并不是单个布尔值，而是一整套组合判断：
- `Skill.CheckCondition()` 会先检查 CD、能量、是否允许空中释放、是否被受击系统禁止、是否被状态效果禁用、是否与已有分身技能冲突等；
- 之后再进入 `ConditionTrigger.Check()`，逐个检查资源配置的条件项；
- 条件项可以是例如 `ConditionGrounded` 这样的具体业务条件。

也就是说，当前“技能能不能开始”已经不只是输入判定，而是一个小型的逻辑系统。

#### 例子 B：子技能命中判定

一个典型子技能，会把逻辑拆成：
- `ConditionNearbyAddEnemy`：先把附近敌人加入潜在目标；
- `CheckAttackBox`：对每个潜在目标进行攻击盒检查；
- 成功后再进入 `DataEffectDefaultDamage`、`DataEffectStatusEffect`、击退、抓取、子弹创建等数据效果；
- 最后再进入表现层的视觉效果任务。

这是一种非常强的业务表达方式：
- 读起来是“先筛目标，再生效”；
- 跑起来是“条件与数据效果分别缓存”；
- 但写法上被拆成了大量 C# 类和资源项。

#### 例子 C：技能结束特例

`SkillEffectProcessorPackageUtil` 里对“技能结束免抓”等逻辑的处理，已经体现了另一类事实：
- 不是所有效果都发生在 `SubSkill.Step()` 期间；
- 有些效果发生在技能开始/结束/打断这种生命周期边界上；
- 它们最终仍然被落到统一的 `EffectProcessor` 执行模型里。

这意味着新语言里也必须有能力表达：
- 常规逐帧流程；
- 生命周期入口；
- 结束 / 打断附加效果。

---

### 4. 执行流程

当前技能系统的运行流程，核心可以压缩成两段：

#### 第一段：切换与调度 (`Step_SwitchSkill`)

这一段负责：
- 递增当前动作帧；
- 判断当前技能是否结束；
- 根据输入尝试启动新技能；
- 处理中断、强制技能、默认技能、死亡技能等。

它的本质是：
**技能主流程调度器。**

一个关键特点是：
- 当前系统把“切换技能”和“执行技能生效”拆到了两个不同 step 中；
- 这对控制顺序很有帮助，但也让主流程被拆散在多个函数与事件里。

#### 第二段：技能生效 (`Step_StepSkill`)

这一段只做一件事：
- `RunningSkill?.Step()`

而 `Skill.Step()` 的核心又是：
1. 准备 Skill 层共享缓存 (`SharedMemories.PrepareSkill`)；
2. 逐个执行 `SubSkill.OnStep()`；
3. 处理技能的阻挡效果等附加流程。

`SubSkill.OnStep()` 又继续做：
1. 准备 `SubEffectPerformer`；
2. 遍历自己的 `SubskillEffectProcessor[]`；
3. `BeginEffectProcessor(e)` 设定 IgnoreId；
4. `e.Execute(effectPerformer, out _)`。

而最终 `EffectProcessor.Execute(...)` 会进行：
1. 进入 effect 级共享内存作用域；
2. 创建并初始化 `EffectContext`；
3. 运行条件；
4. 构建目标列表；
5. 依次执行 `IDataEffect[]`；
6. 再执行 `IVisualEffect[]`；
7. 输出附加结果（如 cancelBullet / hasEnemyTarget）；
8. 回收上下文。

可以看到，当前技能系统已经隐含了一个非常清晰的 VM 原型：
- 有外层流程调度；
- 有中层生命周期入口；
- 有内层效果流水；
- 有显式 context / performer；
- 有共享缓存与作用域栈；
- 但这一切都仍然散落在宿主语言对象图中，而不是统一脚本里。

---

### 5. 这一套方案的优点

1. **业务表达能力强**
   - 技能切换、子技能、效果器、条件、视觉表现都能组合。

2. **静态资源缓存做得很好**
   - `SkillEffectProcessorPackageUtil`、`DataEffectUtil`、`SkillVisualEffectBuilder` 都在尽量复用静态结果。

3. **底层已经开始走向值类型和共享缓存优化**
   - 尤其是 `SharedMemories`、`ComputeMemory` 这条线，说明方向已经对了。

4. **效果器模型统一性不错**
   - 技能、子技能、部分状态效果，都已经复用了 `EffectProcessor`。

---

### 6. 这一套方案的主要痛点

1. **主流程被宿主语言分散得很碎**
   - 技能切换在 `SkillBehaviour`，生效在 `Skill.Step`，真正效果在 `SubSkill` 和 `EffectProcessor`。

2. **阅读时要不断跨类、跨资源、跨缓存跳转**
   - 一个技能的完整语义很难在一个地方看完。

3. **UI 投影困难**
   - 当前结构是“很多对象 + 很多接口 + 很多资源项”的组合，而不是天然可视化的脚本结构。

4. **控制流其实已经存在，但被藏起来了**
   - return、continue、跳过、目标重设、生命周期入口这些语义都有，只是都被分散到了 C# 方法、接口、多态和管理器约定里。

结论：
**技能系统已经非常接近“流程脚本 + 局部逻辑黑盒”的目标形态，但当前写法把语义埋进了太多宿主语言壳层里。**

(7.2) 旧方案二：子弹系统 (BulletBehaviour / BulletTask / BulletEffectProcessor)

子弹系统代表的是另一类旧尝试：
它不是“角色主动释放技能的主流程”，而是“一个脱离角色后仍需每帧自驱运行的实体行为”。

这套系统比技能系统更接近“行为链”，但又没有完全采用行为树，而是用 `ICondition<BulletBehaviourContext>` 串成一个顺序任务流水。

---

### 1. 核心对象关系

可以压缩成：

`BulletBehaviourBuilder -> BulletBehaviour -> BulletTask 链 + BulletEffectProcessor[]`

其中：
- `BulletBehaviourBuilder` 负责从 `IBulletAsset` 构建子弹行为。
- `BulletBehaviour` 是运行时行为体，继承通用 `Behaviour<T>`，内部拿一个顶层 `ICondition<BulletBehaviourContext>` 来跑。
- `BulletTask...` 是子弹逐帧运行的任务节点，例如开始、移动、命中角色、命中地面、重置忽略目标、创建子弹等。
- `BulletEffectProcessor` 则负责“命中角色后，要把哪些子技能效果器借来执行”。

这说明当前子弹系统不是单层结构，而是：
- 一层“子弹自身生命周期任务链”；
- 一层“命中后借技能效果器进行伤害与状态效果结算”。

所以它本质上是“行为链 + 嵌套效果器”。

---

### 2. 构建过程

#### 2.1 BulletBehaviour 的构建

子弹构建从 `BulletBehaviourBuilder.BuildWithCache(bulletAsset)` 开始。
它会缓存 `BulletBehaviour`，这意味着：
- 当前默认假设大量子弹共享同一份静态行为定义；
- 因此任务对象和许多中间结果都倾向于缓存；
- 也因此子弹 Task 明确被要求“视为静态数据”，不能偷偷保存实例级状态。

#### 2.2 BuildEffectProcessors：命中后效果器的构建

`BuildEffectProcessors` 会做两件事：

1. 遍历 `bulletAsset.SkillAsset.SubSkillAssets`，对每个未禁用子技能：
   - 用 `SubSkillEffectProcessorUtil.Create(...)` 构造出一组 `SubskillEffectProcessor[]`；
   - 再包装成 `BulletEffectProcessor`。

2. 兼容旧的 `HitHurtEffect / HitDefenseEffect` 这类已废弃接口。

也就是说，子弹系统并没有自己再发明一整套“伤害判定后怎么办”的逻辑，而是：

> **直接复用技能子技能效果器，把子弹命中也映射成一次“效果器执行”。**

这是非常重要的历史经验，说明“子弹命中”和“技能生效”在底层其实应该是统一的。

#### 2.3 BuildTasks：逐帧任务链的构建

`BuildTasks` 会按顺序拼出子弹的主任务链：
- `BulletTaskStart`
- 移动任务（默认 `BulletTaskUpdatePosition`，或资源自定义 movement task）
- 忽略目标任务
- 其他自定义任务
- `BulletTaskHitActor`
- 如果需要，追加 `BulletTaskHitGround`

最后：
- 如果任务数 > 1，就拼成 `ConditionAnd<BulletBehaviourContext>`；
- 如果只有一个任务，就直接用它；
- 同时通过 `OnTaskBuild` 把嵌套条件里的所有任务收平到 `allTasks`，用于后续扫描初始化接口、请求内存槽位、目标忽略实现等。

这已经是一种“弱结构化行为链”了：
- 没有行为树的 Selector / Sequence / Running 语义；
- 也不是完全随意的蓝图；
- 而是按固定顺序串起来的一组 Task。

---

### 3. 业务举例

#### 例子 A：默认飞行子弹

一个最普通的飞行子弹，通常就会经历：
- `BulletTaskStart`：初始化 frame / totalFrame / collider；
- `BulletTaskUpdatePosition`：根据 `forward * speed` 更新位置；
- `BulletTaskHitActor`：检查角色碰撞并触发效果器；
- `BulletTaskHitGround`：飞出地面边界时播放地面特效并销毁。

这个顺序其实已经非常接近“线性 Flow 脚本”了。

#### 例子 B：特殊弹道

如果子弹需要特殊弹道，比如：
- 延迟运动；
- 曲线运动；
- 围绕角色旋转；
- 朝来源角色回收；
- 批量创建子弹 / 树状子弹；

当前做法是：
- 通过自定义 `IBulletBehaviourTaskAsset.Create()` 产出一个 `ICondition<BulletBehaviourContext>` Task；
- 再由 Builder 将它插入任务链。

这说明子弹系统本质上已经把“逐帧行为”当成一组可插拔 task 来建模。

#### 例子 C：命中角色后套用技能结算

`BulletTaskHitActor` 的核心不是自己结算全部伤害，而是：
- 取出 `assignedEffectProcessors`；
- 根据命中的 `subSkillAsset` 生成 `BulletPerformer`；
- 遍历其中的 `SubskillEffectProcessor[]`；
- 逐个执行它们；
- 根据执行结果决定是否销毁子弹。

这说明子弹系统虽然表面是“行为链”，但真正复杂的业务结算仍然寄托在通用效果器系统上。

换句话说，子弹系统只是多了一层“持续体外壳”。

---

### 4. 执行流程

#### 4.1 初始化阶段

`BulletBehaviourComponent.OnActorInitComplete()` 会：
- 初始化 `BulletBehaviourPerformer`；
- 从 `BulletBehaviourBuilder.BuildWithCache` 取到行为；
- 调 `Behaviour.OnInitComplete(Owner)` 分配 Int / BVector3 等实例数据容量，并调用有初始化需求的 task。

#### 4.2 每帧执行阶段

每帧 `BulletBehaviourComponent.Step()` 会：
1. 初始化 `BulletBehaviourContext`；
2. 调 `Behaviour.OnExecute(context)`；
3. 由顶层 `topTask.Check(context)` 驱动整条任务链。

每个 `BulletTaskBase.Check(context)` 的行为都很像：
- 在编辑器下刷新参数；
- 调 `OnExecute(context)`；
- 如果子弹已经 `WaitingDestroy`，则返回 `False`，从而中断后续任务链。

这是一种非常务实的“短路顺序执行”模型。

#### 4.3 命中角色阶段

`BulletTaskHitActor` 会：
- 更新碰撞体；
- 遍历 `assignedEffectProcessors`；
- 根据子弹等级和子技能资源生成等级数据；
- 初始化 `BulletPerformer`；
- 对每个 `SubskillEffectProcessor` 调 `Execute(...)`；
- 如果结果要求销毁子弹，或者资源配置 `DestroyOnCollision` 且实际命中了敌人，就将子弹置为待销毁。

之后它还会继续处理：
- 对阻挡物的效果；
- InFrameData 结尾逻辑。

#### 4.4 命中地面阶段

`BulletTaskHitGround` 会：
- 判断子弹是否越过工作场景底边界；
- 用 `VisualEffectTaskUtil.CreateTask(...)` 生成视觉任务；
- 通过 `VisualEffectContext` 播放对应表现；
- 然后设置待销毁。

这说明当前子弹系统已经天然拆成：
- 持续运动阶段；
- 命中角色阶段；
- 命中地面阶段；
- 自销毁阶段。

这其实非常适合在新系统里表达成一个更清晰的流程脚本。

---

### 5. 这一套方案的优点

1. **逐帧行为链简单直接**
   - 很多普通子弹逻辑已经自然接近线性脚本。

2. **很好地复用了技能效果器**
   - 没有把伤害、状态效果、表现系统再复制一份。

3. **静态缓存意识很强**
   - Builder、singleton task、请求槽位分配、子弹行为缓存，都是在压运行期开销。

4. **没有引入行为树 Running 这一套包袱**
   - 这点非常重要，说明项目已经在主动回避那种状态难快照的模型。

---

### 6. 这一套方案的主要痛点

1. **主逻辑顺序是靠 task 加入顺序隐式表达的**
   - 读者必须知道 Builder 的拼装顺序，才能理解真实运行顺序。

2. **业务分成两层**
   - 外层是子弹 task 链，内层又嵌套一套 SubSkillEffectProcessor。

3. **“行为链”虽然顺，但不够统一**
   - 普通 movement task、碰撞结算、视觉效果、事件订阅，各自是不同接口和不同范式。

4. **可视化仍然困难**
   - 你可以把 task 顺序画出来，但一旦命中后跳进 EffectProcessor，又会突然进入另一套系统。

结论：
**子弹系统证明了“顺序任务链”对持续实体行为是有价值的，但只靠 task 拼装并不能彻底统一语义；它最终仍然需要一套更上层的脚本化表达来把生命周期、阶段和嵌套效果串起来。**

---

(7.3) 旧方案三：状态效果系统 (StatusEffectAsset / StatusEffect / StatusEffectManager)

状态效果系统代表的是第三类旧尝试：
它不是角色主动技能，也不是单个实体持续行为，而是：

> 一类长生命周期、事件驱动、可叠层、可继承、可跨帧响应的附着逻辑系统。

如果说技能系统偏“主动流程”，子弹系统偏“持续行为”，那么状态效果系统就是偏“被动监听 + 附着修改 + 事件反应”。

---

### 1. 核心对象关系

可以压缩成：

`StatusEffectAsset -> StatusEffectBuilder -> StatusEffect (缓存静态逻辑) -> StatusEffectManager (管理实例) -> StatusEffectData (实例状态)`

其中：
- `StatusEffectAsset` 是资源层描述，包含 applyableEffects、eventAndGroups、freeEffects 等。
- `StatusEffectBuilder` 负责把资源层对象构建成真正运行时 `StatusEffect`。
- `StatusEffectCache` 对构建好的 `StatusEffect` 做静态缓存。
- `StatusEffectManager` 是某个 Actor 身上的运行时管理器，负责增删、事件派发、叠层、过期、全局监听注册、原始事件队列。
- `StatusEffectData` 是每个 Buff/状态效果实例的数据体，记录来源、层数、剩余帧数、自身容器等。

它和技能/子弹系统最大的区别在于：
- 技能和子弹更多是“主动推进”；
- 状态效果更多是“被动等待事件到来，再响应”。

---

### 2. 构建过程

#### 2.1 StatusEffectAsset 的资源内容

当前 `StatusEffectAsset` 的可运行内容大体分三类：

1. `applyableEffects`
   - 应用即生效 / 取消时撤销的效果。
   - 常用于直接改属性、挂程序标记、护盾源等。

2. `eventAndGroups`
   - 一组事件类型对应若干 `EffectGroup`。
   - 当某事件发生时，会调度相应的 EffectGroup。

3. `freeEffects`
   - 当前顶层主要支持 `FreeEffectEventListenerAsset` 这种“事件监听器型顶层效果”。
   - 它底下再挂真正的 free effect 子节点。

#### 2.2 StatusEffectBuilder 的构建流程

`StatusEffectBuilder.Build(asset)` 大致会做：

1. 清空上次残留容器；
2. 遍历 `applyableEffects`：
   - 创建 `IApplyableEffect`；
   - 如有需要，同时创建 `IDamageModifier` / `IHurtDamageModifier`；
   - 收集可销毁对象。

3. 遍历 `freeEffects`：
   - 目前顶层主要要求是 `IFreeEffectAssetTop`，典型实现就是 `FreeEffectEventListenerAsset`；
   - 其子节点再各自调用 `CreateFreeEffect()`。

4. 遍历 `eventAndGroups`：
   - 把各个 `EffectGroupAsset` 变成运行时 `EffectGroup`；
   - 按事件类型注册到 `events` 字典。

5. 将顶层 free effect 监听器也包装成 `EffectGroupFreeEffect`，注册到对应事件上。

6. 最终构建出一个 `StatusEffect(...)`，内部持有：
   - applyableEffects
   - damageModifiers
   - hurtDamageModifiers
   - reapplyViewEffects
   - allEffects
   - allFreeEffects
   - `Dictionary<EventType, IEffectGroup[]>`
   - destroyables

这说明状态效果系统已经形成了另一种成熟范式：

> 资源构建出的不是“线性流程”，而是“按事件索引的一组事件处理器”。

---

### 3. 业务举例

#### 例子 A：应用时修改角色属性 / 标记

`applyableEffects` 很适合做：
- 增减属性；
- 加程序标记；
- 加护盾源；
- 视图重建时重新应用的视觉状态。

这类逻辑的特点是：
- 在 Add / Remove 生命周期边界明确；
- 适合用 Apply/UnApply 成对处理。

#### 例子 B：事件监听式 FreeEffect

`FreeEffectEventListenerAsset` 的设计说明当前系统里已经大量存在这种需求：
- 监听某些事件（如 OnAdd、OnDot、OnUseSkill 等）；
- 事件满足后，再执行一串 free effect。

它本质上是在模拟：
- `event OnAdd { ... }`
- `event OnDot { ... }`
- `event OnEnemyEnterDieSkill { ... }`

只是现在这些东西被拆成了 ScriptableObject + CreateFreeEffect + ConditionList。

#### 例子 C：Buff 内部通过 EffectProcessor 反向复用技能伤害系统

例如 `FreeEffectAttackEnemy`：
- 它不是自己重写整套伤害公式；
- 而是内部临时构建一个 `EffectProcessor`；
- 再用 `StatusEffectEffectPerformer` 驱动一次伤害生效。

这说明状态效果系统又一次证明了：
- 不同业务面最后都在朝“统一效果执行器”靠拢；
- 只是当前它们的外层调度方式不一样。

#### 例子 D：技能命中时添加状态效果

`DataEffectStatusEffect` 则代表另一条链路：
- 技能 / 子技能生效时；
- 通过数据效果给目标添加 `StatusEffectInitialData`；
- 再由目标上的 `IStatusEffectCapable.Add(data)` 接管。

这又一次说明：
- 技能系统和状态效果系统并不是分离世界；
- 它们已经高度互相调用。

---

### 4. 执行流程

#### 4.1 运行时实例管理

`StatusEffectManager` 挂在 Actor 身上，维护：
- `datas`：所有 `StatusEffectData` 列表；
- `map`：按实例 ID 查；
- `dicCount`：按效果类型计数；
- damage / hurt / shield 缓存；
- tagCount 等派生统计；
- pendingRawEvents 队列。

这说明状态效果系统的运行核心，不是某一个对象，而是管理器。

#### 4.2 添加流程

`Add(StatusEffectInitialData)` 最终会走到：
- `DoAdd` / `StackInternal` / `DoRemove` 等；
- `OnAdded(data, index)`；
- `OnApply(data)`；
- `statusEffect.Apply(...)`；
- `statusEffect.RegisterGlobalEvent(...)`；
- 动态事件派发；
- 再补发一个 Add 事件给该状态效果自己。

这说明“添加一个 Buff”并不是简单插表，而是一个完整的小流程。

#### 4.3 帧更新流程

管理器在每帧会做：
- `OnFramePrepare`：清理帧内标记；
- `OnBeforeStep`：减少持续帧数、移除过期状态；
- `OnAfterStep`：统一发送 Dot 事件；
- `OnFrameEnd`：整理移除后的数组、检查原始事件队列是否清空。

这说明状态效果系统本质上也是一个“帧内小调度器”。

#### 4.4 事件执行流程

事件发送时：
- 创建 `StatusEffectContext`；
- 逐个遍历 `datas`；
- 对每个 data 取缓存的 `StatusEffect`；
- `context.BeginStatusEffect(i, statusEffect)`；
- `statusEffect.Execute(context)`；
- 再由 `EffectGroup.Check(context)` 执行具体效果。

`EffectGroup.Check(context)` 内部又会做：
- 间隔判定；
- 条件判定；
- 逐个效果执行；
- 如 `context.Data == null`，说明该状态效果在流程中被移除，立即提前退出。

这也是为什么当前系统里到处强调 `ConditionUtil.ReturnIf(context.Data == null)`：
- 状态效果在执行中可能移除自己；
- 也可能触发新的事件；
- 如果不显式传递 Return / 终止，流程就会乱。

换句话说，状态效果系统已经遭遇了“没有统一脚本流程语义”时最典型的一类问题：

> 宿主语言函数看起来还在继续，但业务语义上当前流程已经无效了。

---

### 5. 这一套方案的优点

1. **非常适合表达长期附着逻辑**
   - 叠层、持续时间、来源、继承、全局事件注册等都很自然。

2. **事件驱动非常强**
   - OnAdd / OnRemove / Dot / 技能开始结束 / 角色死亡等都能接。

3. **局部能力复用很强**
   - 既能直接改属性，也能借效果器做伤害、加 Buff、派发事件。

4. **运行时管理非常严谨**
   - 管理器把顺序、叠层、原始事件队列、移除整理等都管得很严。

---

### 6. 这一套方案的主要痛点

1. **概念层次很多**
   - applyableEffects / freeEffects / eventAndGroups / raw events / dynamic events / effect group / effect / free effect / modifier 等层次非常多。

2. **流程严重分散在“事件 + 约定 + 注释”里**
   - 阅读某个 Buff 的完整行为，必须脑中模拟 Add、Remove、SendEvent、RawEvent 队列、group interval、ReturnIf 等多重机制。

3. **宿主语言控制流和业务控制流错位**
   - 函数还没 return，但 Buff 可能已经被移除；
   - 当前执行上下文随时可能失效。

4. **非常难做清晰可视化**
   - 因为它本质上不是一条线性的主流程，而是一个“事件触发网”。

结论：
**状态效果系统证明了“纯事件驱动 + 模块式效果器”可以覆盖大量业务，但它也最明显地暴露出：当流程跨事件、跨移除、跨生命周期时，如果没有一个统一脚本语义，作者和维护者会不断依赖约定、注释和 ReturnIf 之类的补丁式规则。**

---

(7.4) 三套旧方案的共同特点与共同痛点

这三套东西表面差异很大，但底层其实已经有不少共同点：

### 共同特点

1. **都在追求“静态资源”和“实例状态”的分离**
   - 技能缓存 SkillEffectProcessorPackage；
   - 子弹缓存 BulletBehaviour；
   - 状态效果缓存 StatusEffect。

2. **都已经不满足于纯配置表驱动**
   - 都需要结构化组合能力。

3. **都依赖显式 Context / Performer 传值，而不是直接依赖宿主对象图调用栈**
   - `EffectContext`
   - `BulletBehaviourContext`
   - `StatusEffectContext`
   - 各类 Performer

4. **都在逐渐走向统一效果执行器**
   - 子技能直接用 `EffectProcessor`；
   - 子弹命中借 `SubskillEffectProcessor`；
   - 状态效果里也会反向借 `EffectProcessor`。

5. **都已经对性能和实例隔离有警惕**
   - 缓存、singleton、请求槽位、共享内存、避免实例状态污染等到处可见。

### 共同痛点

1. **主流程隐藏在宿主语言对象分发中**
   - 真正的业务顺序散落在 Builder、Manager、Task、Condition、Effect、事件派发里。

2. **很难整体阅读**
   - 一个业务逻辑经常跨多个类、多个资源、多个回调点。

3. **很难直接映射到干净 UI**
   - 现在的结构天然更适合程序组合，不适合直接给策划看清楚“完整过程”。

4. **快照和回滚模型不统一**
   - 技能、子弹、状态效果虽然都在努力规避问题，但依然没有被统一到同一种“脚本状态快照”语义里。

5. **控制流已经复杂到需要一等公民支持**
   - Return / Continue / Running 的替代物、事件离开当前流程、生命周期边界、阶段推进，这些都已经客观存在。

### 更主观的一层压缩判断

在上面的客观回顾之外，还可以再压缩出一层更直接面向“新架构为什么必须出现”的判断。

#### 1. 技能方案的本质边界

技能方案本质上是：
**围绕 `EffectProcessor` 组织出来的一套主流程调度层。**

它的主要痛点可以更直接地概括成：

1. **天然倾向平铺逻辑，对复杂分支的支持不足**
   - 现在的技能效果器很适合表达“顺着跑一遍的标准生效流水”。
   - 一旦分支复杂，往往就会退化成：
     - 多个条件组；
     - 多个子技能；
     - 多个效果器；
     - 多次目标选择 / 条件检查；
     - 额外状态或额外约定。
   - 这会带来重复计算，也会让 authoring 趋向平铺。
   - `ComputeMemory` 和共享缓存确实缓解了一部分重复计算与临时数据问题，但它更多是底层优化，并没有从策划/作者视角根本改变“逻辑写法偏平铺”的问题，因此感知并不强。
   - 因此，“分支支持良好”本身应被视为新系统的硬需求，而不是可有可无的附属优化。虽然它看起来会随着脚本化自然改善，但在设计上仍然需要被明确守住。

2. **挂起能力不足，但又不希望退回行为树 Running**
   - 当前技能系统有开始、持续、结束、打断、子技能逐帧执行这些生命周期。
   - 但它没有把“挂起/等待/恢复”做成脚本层一等语义。
   - 于是很多本质上应该写成 `wait` 的东西，只能拆散在外层流程、动作帧、事件和多个对象之间。
   - 与此同时，这个项目又明确不想退回行为树那种 `Running` 节点挂起方式。
   - 更直接地说，行为树虽然确实能处理客观存在的挂起需求，但它的表达手段过于束手束脚，并且 `Running` 这种挂起模型本身并不是这里想要的方向。

3. **理想终点其实是虚拟机，而当前形态离虚拟机还很远**
   - 当前已经有一些明显朝 VM 靠拢的迹象：
     - `Context / Performer` 显式传值；
     - `SharedMemories / ComputeMemory`；
     - 条件 / 目标 / 数据效果 / 表现效果 的流水拆分。
   - 但整体仍然主要依附宿主语言对象图和接口分发。
   - 也就是说，当前实现更像“在 C# 对象系统里模拟脚本执行”，而不是“已经进入统一 VM 状态模型”。
   - 从这个角度看，它的理想方向确实更像虚拟机，而不是继续在现有资源拼装方式上补更多规则。

#### 2. 子弹方案的更准确定位

子弹方案的真正优点，不是它自己独立解决了全部战斗逻辑，而是：
**它很好地表达了“对象行为组合”这件事。**

例如：
- 逐帧移动；
- 特殊弹道；
- 命中角色；
- 命中地面；
- 创建子弹 / 子弹树；
- 忽略目标管理；
- 到时自销毁。

这些都很符合“一个持续存在的对象应该如何行动”的直觉。

但它的底层伤害、状态效果、目标判定、表现播放，仍然大幅依赖技能效果器系统复用。
因此，它更准确的定位是：

> **子弹方案更像是在效果器内核之外，补出了一层“对象行为组合外壳”。**

这也意味着：
- 子弹方案证明了“对象行为组合”是有必要的；
- 但它并没有提供一套真正独立、统一的新底层逻辑模型。

#### 3. 状态效果方案的更准确定位

状态效果方案可以看成：
**对效果器方案的一次优化和补丁化扩展。**

它做成这件事的方式是：
- 不再只靠平铺效果器顺序执行；
- 而是引入事件监听、Group、间隔、附着生命周期、Apply/UnApply、RawEvent 等机制；
- 这样一来，某些“什么时候触发”的业务问题就比纯技能效果器更好表达。

因此，它确实：
- **部分改善了分支与触发粒度问题**；
- **更适合长期附着、事件驱动、状态反应型业务**。

但它仍然没有真正解决挂起问题：
- 它只是把复杂流程分散到了事件监听器、Add/Remove 生命周期、原始事件队列、`ReturnIf(context.Data == null)` 这类补丁式规则中；
- 它解决的是“如何按事件切开逻辑”，不是“如何把挂起本身做成一等语义”。

换句话说：
- 技能方案更多是“平铺生效链”；
- 状态效果方案更多是“事件化生效网”；
- 但两者都还没有进入“显式挂起状态机 / 虚拟机状态”这一层。

#### 4. 当前最核心的架构矛盾

这里存在一个必须正面承认的矛盾：

1. **为了支持帧同步、快照、导入导出与回滚，底层天然希望逻辑尽量偏瞬态**
   - 也就是：
     - 少对象；
     - 少宿主语言调用栈残留；
     - 更多连续值类型状态；
     - 更容易拷贝、恢复、回滚。

2. **但业务客观上又大量需要挂起能力**
   - 技能阶段切换；
   - 等待若干帧；
   - 等待命中；
   - 等待事件；
   - 等待窗口结束；
   - 持续效果的延后恢复。

所以这里不能简单二选一：
- 不能为了快照便利，就彻底拒绝挂起；
- 也不能为了挂起便利，就退回宿主协程或行为树 `Running` 这种不利于快照的模型。

真正需要的，是一种：

> **偏瞬态、但原生支持挂起的模型。**

也就是：
- 挂起不是宿主调用栈残留；
- 挂起不是行为树节点内部的 `Running`；
- 挂起应该被压缩成显式状态，例如：
  - `IP`
  - `Wait`
  - `Registers / State`

这实际上正是新脚本形式与 VM 最核心的目标之一：

> 在不向行为树妥协的前提下，把“业务需要挂起”和“底层需要可快照的偏瞬态执行”统一起来。

最终结论是：

> 新的胶水执行器 / 技能 VM，不是从零凭空发明一套语言，而是把这三套旧系统中已经客观存在、但目前分散在 C# 对象与资源拼装里的流程语义，统一抬升到脚本层，并正面解决“偏瞬态快照”与“业务挂起需求”之间的矛盾。

---

(8) 对 结构化流程图、蓝图、行为树 的适配结论

这一部分的目的不是抽象讨论 UI，而是明确：
**哪种可视化方式更适合当前项目，哪种不适合，以及原因是什么。**

---

(8.1) 对行为树 (Behavior Tree) 的看法

行为树的强项是：
- 层级结构清晰；
- Selector / Sequence 语义成熟；
- AI 决策类逻辑易于组合；
- “成功 / 失败 / 运行中”是一套非常经典的控制模型。

但它和当前项目的核心需求不匹配，原因主要有四个：

1. **行为树天然依赖 Running 语义**
   - 而当前项目恰恰希望规避 Running 这种额外状态枚举与宿主调用栈耦合。
   - 你要的是 `wait` 后保存 IP 和寄存器，不是节点自己半悬着。
   - 更进一步地说，行为树虽然能覆盖一部分挂起需求，但这种挂起方式并不等于这里需要的“可快照、可恢复、偏瞬态”的挂起。

2. **行为树天然把控制流压扁成树语义**
   - Sequence / Selector / Decorator 这类结构很适合“决策”，
   - 但不适合技能、子弹、状态效果里大量存在的：
     - 时间推进；
     - 生命周期函数；
     - 副作用调用；
     - 事件触发；
     - 复杂数据过滤与结算。
   - 从表达体验上说，它也会让 authoring 变得束手束脚，本来可以自然写成流程和函数的东西，被迫绕到树节点语义里去。

3. **行为树不擅长表达普通函数式局部逻辑**
   - 公式、局部推导、短路表达、结构体拼装等，一旦强行树化，会很不自然。

4. **行为树会反向限制语义设计**
   - 一旦 UI 以行为树为核心，语言层很容易被迫围着行为树那套节点语义设计。
   - 这会让本来应该自然表达的战斗流程，变成为了适配树而写的伪逻辑。

因此，结论非常明确：

> 行为树不应该成为本项目新脚本系统的主 UI 形式。

它最多只能在某些特殊 AI 场景里局部存在，但不适合作为技能 VM / 胶水执行器的总表达模型。

---

(8.2) 对蓝图式可视化脚本 (Blueprint / 自由连线图) 的看法

蓝图之所以是主流，并不是偶然。它背后有一整套现实原因：

1. **表达能力非常通用**
   - 任意节点、任意连线、任意回调、任意数据流，几乎都能往里装。

2. **对非程序用户很友好**
   - 拖节点、看参数、找功能，比纯文本 discoverability 更强。

3. **容易复用现成 node editor 基础设施**
   - Inspector、Pin、调试高亮、节点菜单，这一整套编辑器生态都能直接复用。

4. **局部调试演示很直观**
   - 当前执行到哪个节点、哪条线走了、参数是什么，展示效果非常好。

所以从通用引擎视角看，蓝图是非常合理的主流选择。

但是，本项目和“通用可视化脚本”场景有几个关键差异：

### 关键差异 1：脚本文本才是唯一真理源

当前项目的目标不是“图就是源代码”，而是：
- 脚本是 source of truth；
- UI 是投影、调试和辅助搭建工具。

这会直接改变蓝图的地位：
- 它不再需要承担全部 authoring 责任；
- 它更适合作为局部展开视图，而不是总视图。

### 关键差异 2：战斗逻辑里有大量密集局部逻辑

技能、子弹、状态效果中大量逻辑其实是：
- 条件过滤；
- 目标选择；
- 公式判断；
- 局部数据拼装；
- 分支短路。

这些东西一旦完全蓝图化，很容易：
- 线爆炸；
- 局部公式表达难看；
- 小改动牵一大片；
- 文本与图之间的 round-trip 极不稳定。

### 关键差异 3：当前项目更关注“时间与状态”而不是“任意拼图”

蓝图擅长的是：
- 任意依赖；
- 任意拼接；
- 任意事件回调；
- 任意数据线传递。

而当前项目最核心的问题其实是：
- `wait`；
- 生命周期；
- 阶段切换；
- 副作用边界；
- 状态快照；
- 回滚恢复。

也就是说，当前项目的主问题轴不是“任意开放图”，而是“时间结构 + 状态结构”。

因此，结论应该是：

> 蓝图不是完全不适合，而是不适合作为主视图与唯一可视化形态。

它更适合：
- 做局部特殊节点的展开；
- 做少数复杂数据流的内部视图；
- 做调试辅助；
- 做编辑器能力发现入口。

而不适合作为整个技能 VM 的主 authoring 结构。

---

(8.3) 对结构化流程图 (Structured Flow Graph) 的看法

结构化流程图的风险在于：
- 如果只是把 AST 每一句话照抄成节点，
- 那它确实会“太像代码截图”，从而失去 UI 意义。

但是，结构化流程图并不等于“代码逐句画图”。

只要 UI 做的是**语义升维**，它仍然非常有价值。

所谓语义升维，指的是 UI 不再只是重复源码，而是重点展示源码不擅长直接表达的东西：
- 入口与出口；
- `wait` / 挂起点；
- 主要分支；
- 阶段切换；
- 副作用节点；
- 状态读写；
- 当前执行位置；
- 黑盒逻辑边界；
- 调试时的历史路径。

换句话说，结构化流程图真正有价值的前提是：

> 它展示的是“流程语义”，而不是“源码字面形式”。

### 为什么它更适合当前项目

1. **与脚本为源的前提相容**
   - 文本先写好，图负责稳定投影。

2. **与时间推进语义相容**
   - `wait`、阶段切换、生命周期入口，都能自然显示。

3. **更适合技能 / 子弹这种主流程**
   - 顺序、分支、循环、调用，非常容易结构化展示。

4. **比蓝图整洁得多**
   - 不需要让所有局部逻辑都变成满屏连线。

5. **不会像行为树那样强行束缚语义**
   - 结构化流程图可以保留普通函数控制流，不必退化成 Sequence / Selector / Running 那套模式。

因此，结构化流程图是可以成为主视图的，但前提必须明确：

- 它不是“逐句 AST 画图”；
- 它必须突出流程关键语义；
- 对不适合展开的内容要允许降级为特殊节点或黑盒节点。

---

(8.4) 三者与本项目的最终适配判断

### 行为树
- **适配度：低**
- 原因：语义被 Running / Sequence / Selector 束缚，不符合当前项目对挂起、快照、回滚、函数逻辑自由度的需求。

### 蓝图式自由连线图
- **适配度：中（局部适合，全局不适合）**
- 原因：局部复杂图、编辑器 discoverability、调试展示有价值；但若作为主视图，极易炸线，也会反向绑架脚本语法。

### 结构化流程图
- **适配度：高（适合作为主视图）**
- 原因：与脚本为源、时间推进、阶段表达、主流程阅读最相容；同时保留普通函数式书写体验。

---

(8.5) 当前项目更合适的 UI 组合方案

最终更适合本项目的不是三选一，而是分层组合：

### 主视图：结构化流程图
用于展示：
- `[Flow]` 主流程；
- if / else / switch / loop；
- wait / suspend 节点；
- 调用动作；
- 入口 / 出口；
- 主要状态读写。

### 副视图：阶段 / 时间轴视图
用于展示：
- 每个 `wait` 前后的阶段切分；
- 技能起手 / 生效 / 收招；
- 子弹阶段；
- Buff 生命周期中的阶段点。

### 兜底视图：黑盒脚本节点 / 局部蓝图展开
用于承接：
- `[Logic]` 普通函数；
- 复杂公式；
- 局部密集数据流；
- 少数不适合主视图展开的破坏性语法。

也就是说：
- **主视图不走行为树；**
- **整体不走纯蓝图；**
- **主体采用结构化流程图；**
- **局部保留蓝图/黑盒的逃生舱。**

这和当前项目的语言目标是完全一致的：
- 保证文本书写体验；
- 保证 UI 整洁；
- 对冲突点用特殊 UI 形式处理；
- 不让 UI 反向控制语言本体。

---

(8.6) 这一轮讨论对新脚本形式的直接影响

把上面的结论翻译成脚本设计要求，就是：

1. `[Flow]` 应该更像普通函数，而不是行为树节点描述。
2. `[Logic]` 应该保留普通函数最大自由度，不应图形化展开。
3. `wait` 应该成为一等公民，因为它既是执行语义，也是 UI phase 切分点。
4. 语言层要优先保证“好写、直觉、不啰嗦”，而不是优先服务蓝图展开。
5. UI 的责任不是替代文本，而是把：
   - 时间结构；
   - 阶段结构；
   - 状态结构；
   - 副作用边界；
   - 当前执行位置；
   提炼出来。

最终总结：

> 对当前项目来说，最合适的方向不是行为树，也不是把所有东西都做成自由蓝图，而是：
> 以脚本文本为唯一真理源，以结构化流程图为主 UI，以阶段/时间轴视图强化时序语义，以黑盒脚本节点或局部蓝图展开承接少数复杂局部结构。

后续方向:
需求驱动
尽可能多、尽可能全地列业务例子
再反推脚本/VM 设计是否能理论上覆盖
最后从候选方案里选最适合的
