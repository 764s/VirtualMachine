基于我们之前对三套旧方案的压缩回顾、UI 适配结论、脚本形式选型、前端发展启示以及历史失败教训的讨论，我整理出以下**关键需求清单**。这些需求将作为脚本语言、虚拟机以及编辑器工具链的核心设计准则。

---

## 一、语言层关键需求

### 1.1 结构与逻辑的自然表达
- **需求**：脚本语言应允许作者以最自然的方式书写技能、子弹、状态效果等战斗逻辑，无需为了“结构/逻辑分离”而人为拆散代码。
- **实现**：采用**视图驱动模型**——语言层不强制 `[Flow]` / `[Logic]` 标记，所有函数默认可包含 `await`、分支、循环；编辑器在生成流程图时自动将不包含 `await` 的子树折叠为黑盒节点。作者可通过可选的 `[Logic]`（强制折叠）或 `[Flow]`（强制展开）覆盖默认行为。
- **借鉴**：前端框架（如 React）的 JSX 允许在声明式中嵌入逻辑，但通过工具（如 ESLint）和组件化边界保持清晰；我们应提供类似的灵活性，而非语法枷锁。

### 1.2 一等公民的异步挂起
- **需求**：原生支持 `await` / `wait` 语义，用于表示等待帧数、动画、事件、命中判定等。挂起必须转换为显式状态（IP + 寄存器），而非依赖宿主语言调用栈或行为树的 `Running` 状态。
- **实现**：`await` 编译为 VM 的挂起指令，保存当前指令指针和寄存器，让出执行权，下次唤醒时直接恢复。编译器将包含 `await` 的函数自动转换为状态机。
- **借鉴**：C# 的 `async/await` 状态机拆分、XState 的状态图概念；避免像 ASP.NET ViewState 那样自动序列化所有状态。

### 1.3 强类型与结构体拍平
- **需求**：脚本支持自定义结构体，但在底层必须拍平为连续的寄存器槽位，禁止运行时对象分配，以实现零 GC 和快速快照。
- **实现**：结构体定义在源码中，编译器在分配寄存器时将结构体成员展开为独立的寄存器槽位。结构体传递时按值拷贝寄存器段，无堆分配。
- **借鉴**：C# 的 `struct` 和 `Span<T>` 理念；避免像早期 JavaScript 对象那样导致 GC 压力。

### 1.4 局部计算与跨 await 数据的编译器分析
- **需求**：编译器应能自动分析变量的生命周期，将不跨 `await` 的局部变量分配在临时寄存器中，并在 `await` 后复用；跨 `await` 的变量提升到持久寄存器。无需作者手动标记。
- **实现**：在生成状态机时，通过数据流分析确定每个变量在 `await` 前后的使用情况，生成高效的寄存器分配方案。
- **借鉴**：Svelte 的编译时分析；避免像 GWT 那样抽象泄漏。

### 1.5 完整的调试信息支持
- **需求**：脚本执行时，编辑器必须能够断点、单步、查看变量值，且源码位置与 VM 指令准确映射。
- **实现**：编译器生成字节码时附带调试符号（行号、变量名、作用域）。VM 提供调试接口，支持暂停、步进、寄存器读取。
- **借鉴**：TypeScript 的 source map；避免像 GWT 或 Flash 时代码难以调试。

## 二、虚拟机层关键需求

### 2.1 偏瞬态寄存器模型
- **需求**：虚拟机采用寄存器架构，无栈帧，执行状态仅由指令指针（IP）、挂起计数器（WaitFrames）、寄存器数组（Registers[]）组成。所有数据均为值类型，无对象引用。
- **实现**：寄存器数组在角色/子弹/Buff 实例初始化时预分配固定大小（根据脚本最大寄存器需求）。执行时直接读写寄存器。
- **借鉴**：Lua 5.x 的寄存器虚拟机；但我们需要更激进的静态分配。

### 2.2 零分配快照与回滚
- **需求**：虚拟机状态（IP + WaitCounter + Registers[]）必须能被整体保存和恢复，仅通过 `memcpy` 完成，不触发任何 GC 或深拷贝。
- **实现**：状态打包为一个连续值类型结构体，支持 `SaveState` / `LoadState`。回滚时直接覆盖寄存器数组。
- **借鉴**：Redux 的不可变状态快照；避免像 ViewState 那样自动序列化。

### 2.3 字节码静态生成与回填
- **需求**：脚本编译为字节码数组，所有跳转地址在编译期通过回填（backpatching）确定，无运行时动态跳转表。
- **实现**：编译器遍历 AST，为每个基本块生成指令，记录未决跳转地址，最后回填。
- **借鉴**：传统编译器技术；避免像动态语言那样频繁解释或 JIT 编译。

### 2.4 系统调用表（Syscall Table）热替换
- **需求**：脚本通过统一的系统调用表调用宿主功能（如移动、伤害、播放特效）。支持在运行时替换调用实现（例如用于测试、调试或热修复）。
- **实现**：系统调用表是一组函数指针数组，脚本通过索引调用。可动态替换表中条目。
- **借鉴**：操作系统 syscall 机制；避免硬编码宿主函数。

## 三、UI 与工具层关键需求

### 3.1 结构化流程图作为主视图
- **需求**：编辑器以结构化流程图为主视图，展示 `[Flow]` 主流程的骨架（顺序、分支、循环、等待），而不是逐句展开所有细节。
- **实现**：从脚本 AST 生成流程图节点，仅显示“语义节点”（如调用、分支、等待），普通表达式不产生节点。流程图支持折叠/展开、钻取。
- **借鉴**：XState 的状态图可视化；避免像 Flash 时间轴那样混合视图。

### 3.2 黑盒逻辑块自动折叠
- **需求**：不包含 `await` 的代码块（如条件判断中的纯计算、局部变量赋值）在流程图上自动折叠为黑盒节点，双击展开查看内部表达式。
- **实现**：编译器在生成流程图元数据时，标记每个节点的“是否为黑盒”。编辑器根据此标记决定折叠行为。
- **借鉴**：Svelte DevTools 的组件树折叠；避免像 ASP.NET 控件树那样全部展开。

### 3.3 阶段/时间轴视图
- **需求**：提供辅助视图，以时间轴方式展示 `await` 划分的阶段，便于理解技能的起手、生效、收招等阶段。
- **实现**：扫描脚本中所有 `await` 点，将函数切分为阶段列表，每个阶段显示其主要操作（调用、分支）。
- **借鉴**：现代前端 DevTools 的网络时序图；Flash 的时间轴但更语义化。

### 3.4 调试面板集成
- **需求**：编辑器内集成调试器，支持断点、单步、寄存器查看、快照回滚。
- **实现**：VM 提供调试协议，编辑器通过协议控制执行和读取状态。
- **借鉴**：Chrome DevTools；避免 GWT 那种“编译后难调试”。

### 3.5 源码映射与双向定位
- **需求**：点击流程图节点能跳转到对应源码行；源码中可设置断点，在流程图上高亮。
- **实现**：编译时生成源码位置与字节码/流程图节点的映射表。
- **借鉴**：Webpack 的 source map；避免 XSLT 那种无源码定位。

## 四、演进与扩展性关键需求

### 4.1 语言前端可替换
- **需求**：脚本的语法前端（词法/语法分析）应可替换，支持未来切换到其他宿主语言（如直接写 C# 代码配合 Roslyn 分析，或使用 Lua 配合宏）。
- **实现**：核心是统一 AST 结构和语义模型。前端将文本解析为 AST，后续编译流程（类型检查、寄存器分配、字节码生成）完全基于 AST，与前端无关。
- **借鉴**：LLVM 的前端分离；避免 XBL 那种绑定特定实现。

### 4.2 编译器与 VM 平台中立
- **需求**：脚本编译器和 VM 应不依赖特定游戏引擎或宿主语言特性，以便未来移植到其他项目。
- **实现**：系统调用表抽象所有宿主交互；VM 仅依赖 C# 标准库（或可移植的 C++ 后端）。快照数据格式独立。
- **借鉴**：Lua 的跨平台设计；避免 Web Components v0 的浏览器绑定。

### 4.3 渐进式迁移旧系统
- **需求**：新脚本系统应允许逐步替换现有的技能、子弹、状态效果，而非一次性重写所有。
- **实现**：提供从旧资源到脚本的转换工具（半自动）；支持在旧系统中嵌入脚本调用，反之亦然。VM 可被旧系统驱动。
- **借鉴**：TypeScript 的渐进式迁移策略；避免像 GWT 那样全量重写。

## 五、从历史教训中提取的约束清单

| 失败尝试 | 核心教训 | 对我们的约束 |
|----------|----------|-------------|
| XSLT | 复杂的转换语言不可维护 | 禁止为 Logic 设计独立的子语言，必须与 Flow 共享表达式语法。 |
| XBL / HTC | 隐式绑定导致调试困难 | 所有组件组合必须显式调用，禁止隐式“魔法”。 |
| ASP.NET ViewState | 自动序列化导致性能灾难 | 状态快照必须由作者显式触发，且仅拷贝连续值类型。 |
| Flash 可视化脚本 | 可视化与代码混合导致混乱 | UI 必须严格分离：主视图为结构化流程图，复杂逻辑降级为黑盒。 |
| AMD/CMD 模块 | 冗余语法增加心智负担 | 直接采用宿主语言的模块系统（如 C# 的 using/namespace）。 |
| GWT | 抽象泄漏 + 调试困难 | 保留源码映射，VM 支持调试信息，不隐藏宿主特性。 |
| Web Components v0 | 单一实现 + 生态不足 | VM 设计必须跨平台（C# / C++ / 其他），不依赖特定引擎 API。 |

---

## 总结：关键需求清单（精简版）

1. **语言层**  
   - 视图驱动分类（默认无标记，编辑器自动折叠）。  
   - 一等公民 `await`，编译为状态机。  
   - 强类型结构体，编译期拍平为寄存器。  
   - 编译器自动分析局部变量生命周期，优化寄存器分配。  
   - 完整的调试符号与源码映射。

2. **虚拟机层**  
   - 寄存器架构，状态 = IP + WaitCounter + Registers[]。  
   - 零分配快照（memcpy 级）。  
   - 静态字节码，跳转地址编译期回填。  
   - 系统调用表可热替换。

3. **UI/工具层**  
   - 结构化流程图主视图，自动折叠黑盒逻辑块。  
   - 阶段/时间轴辅助视图。  
   - 集成调试器（断点、单步、寄存器查看、回滚）。  
   - 双向源码定位。

4. **演进与迁移**  
   - 前端可替换（支持未来换语言）。  
   - VM 平台中立。  
   - 渐进式迁移旧系统。

这些关键需求将作为我们下一步脚本设计与实现的“宪法”，确保我们不会重蹈历史覆辙，同时充分吸收现代语言与工具的成熟经验。
