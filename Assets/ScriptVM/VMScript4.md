# FFEditor 胶水执行器与技能虚拟机架构总纲（第四部：阶段性结论与工程化需求收束）

> 本文用于压缩整理 `VMScript.md`、`VMScript2.md`、`VMScript3.md` 的讨论结果，形成一份更适合作为项目立项摘要、架构共识说明与后续设计约束基线的文档。

---

## 一、项目立项版摘要

### 1.1 当前问题的本质

现有战斗逻辑并不是缺少功能，而是已经在长期演化中分裂成了三套各自有效、但整体不统一的体系：

- 技能系统：擅长表达角色主动释放的主流程；
- 子弹系统：擅长表达脱离角色后的持续体行为；
- 状态效果系统：擅长表达附着式、事件驱动、跨帧响应逻辑。

这三套系统都已经沉淀出不少共通能力：

- 生命周期管理；
- 条件判断与目标选择；
- 数据效果与表现效果执行；
- 上下文隔离；
- 静态缓存；
- 对性能与实例隔离的警惕。

但它们也共享同一类瓶颈：

- 主流程分散在宿主语言对象图、Builder、Manager、Task、Condition、事件派发之中；
- 很难在一个地方完整阅读一个业务；
- 很难稳定映射为干净、清晰的编辑器 UI；
- 挂起、等待、生命周期边界、事件离开当前流程等控制语义没有成为一等公民；
- 快照、回滚与状态恢复始终没有被统一到同一种执行模型里。

因此，当前真正需要的不是再补一层规则，而是把这些已经分散存在的流程语义统一抬升到脚本层，并在底层用一套明确的虚拟机状态模型承载它们。

---

### 1.2 新系统的目标

目标不是做一个“能跑逻辑的小脚本语言”，而是做一套：

- 面向 2D 横版动作游戏战斗业务的；
- 统一技能 / 子弹 / 状态效果三类逻辑的；
- 以脚本文本为唯一真理源的；
- 以结构化流程图为主 UI 投影的；
- 原生支持 `wait / await` 挂起的；
- 适合帧同步、预测回滚、快速快照的；
- 偏瞬态、零 GC、可高性能执行的；
- 可渐进替换旧系统的；

**胶水执行器 / 技能虚拟机架构。**

这个系统的核心使命，是统一下面这组长期冲突的要求：

1. 业务上大量需要挂起、等待、阶段切换、事件响应；
2. 底层上又必须保持状态简单、可压缩、可拷贝、可回滚；
3. 脚本书写必须自然，不应为了编辑器投影强行扭曲；
4. 可视化必须清晰，但不能反向绑架语言本体；
5. 性能必须至少不弱于现有可接受方案，并且战斗期严禁运行时分配。

---

### 1.3 新系统的目标形态

最终想要的不是行为树，不是纯蓝图，也不是继续把业务语义藏在 C# 对象和资源拼装里。

最终目标更接近这样一套组合：

- **脚本文本**：唯一真理源；
- **结构化流程图**：主视图，用于展示主流程、分支、阶段、等待点；
- **基于 `await` 的视图驱动展开**：编译器自动分析 AST，含挂起链路的函数自动展开，纯逻辑默认折叠为黑盒节点；
- **阶段 / 时间轴视图**：辅助展示技能起手、生效、收招，以及子弹 / Buff 的阶段变化；
- **黑盒逻辑节点 / 局部蓝图展开**：承接不适合大面积展开的局部复杂逻辑；
- **寄存器式 VM**：用显式状态承载执行，而不是依赖宿主调用栈；
- **RAM 的 ECS 组件化映射**：`IP / Wait / Registers` 以纯值类型组件直接挂在执行实体上；
- **句柄化批处理通道**：多目标横向批处理与复杂临时数据通过宿主 Syscall + `Int Handle` 流转；
- **系统调用表（Syscall Table）**：把宿主引擎能力接入脚本层；
- **显式清理语义**：通过 `defer` / `Cleanup` 等机制保证强制打断时宿主状态不泄漏；
- **ROM / RAM 分离的执行架构**：静态脚本资产与实例运行状态彻底分离。

---

### 1.4 成功标准

新系统如果要被认为是成功的，至少应满足以下结果：

1. **业务覆盖成功**
   - 能同时覆盖技能主流程、子弹持续行为、Buff 事件反应三类核心业务；
   - 能表达生命周期入口、等待、阶段切换、嵌套效果调用与局部逻辑计算。

2. **执行模型成功**
   - `wait / await` 成为一等语义；
   - 挂起被压缩为显式状态，而不是宿主栈残留或行为树 `Running`。

3. **性能模型成功**
   - 战斗中零运行时 GC；
   - 快照 / 回滚接近纯内存拷贝；
   - 宿主语言 + VM 的综合效率不低于纯 Lua 封闭逻辑方案。

4. **工具链成功**
   - 编辑器能稳定显示流程、阶段、当前执行位置；
   - 支持断点、单步、变量查看、源码映射。

5. **工程落地成功**
   - 可以渐进替换旧系统，而不是必须一次性重写；
   - 前端语法可演进，但核心 AST / VM 模型应尽量稳定。

## 二、核心架构结论

### 2.1 新系统本质上是在统一旧系统中已经存在的流程语义

它不是从零发明一个抽象 DSL，而是在把旧系统中早已客观存在、但目前被分散隐藏的语义统一抬升出来：

- 技能切换；
- 子技能逐帧运行；
- 子弹任务链；
- Buff 的 Add / Remove / Event 响应；
- 条件 -> 目标 -> 数据效果 / 表现效果 的标准流水；
- 生命周期边界；
- 中断、提前退出、短路、阶段推进；
- 等待若干帧、等待命中、等待事件。

换句话说，新系统不是发明新需求，而是给既有需求找到一套更统一、更可维护、更可快照的承载模型。

---

### 2.2 结构化流程图应成为主 UI，不应走行为树或纯蓝图路线

结论已经相对明确：

#### 行为树不适合作为主表达模型

原因主要有：

- 太依赖 `Running`；
- 不适合当前项目对快照 / 回滚 / 显式挂起的要求；
- 会把本来更自然的流程语义压扁成树节点语义；
- 不适合大量普通函数式局部逻辑。

#### 纯蓝图不适合作为唯一主视图

原因主要有：

- 会炸线；
- 不适合战斗逻辑中密集的局部计算与公式；
- 容易反向绑架语法设计；
- 不符合“脚本文本才是真理源”的目标。

#### 结构化流程图最适合作为主视图

因为它更适合展示：

- 顺序；
- 分支；
- 循环；
- `wait` / suspend 点；
- 生命周期入口；
- 阶段切换；
- 当前执行位置；
- 黑盒逻辑边界。

因此，更合适的 UI 组合是：

- 主视图：结构化流程图；
- 副视图：阶段 / 时间轴；
- 兜底：黑盒脚本节点 / 局部蓝图展开。

---

### 2.3 `wait / await` 是整套系统的第一关键语义

当前项目的核心问题不是“如何做任意节点拼图”，而是：

- 如何表达时间推进；
- 如何表达挂起与恢复；
- 如何表达阶段变化；
- 如何让这些状态天然支持快照与回滚。

因此，`wait / await` 不是附属语法糖，而是：

- 执行语义的核心；
- UI 阶段切分的核心；
- VM 状态建模的核心；
- 替代行为树 `Running` 的关键机制。

新系统必须保证：

- 挂起不会残留宿主调用栈；
- 挂起不会以对象树局部状态的形式散落；
- 挂起会被压缩成显式值类型状态，例如：
  - `IP`
  - `WaitFrames`
  - `Registers[]`

---

### 2.4 底层执行模型应是偏瞬态的寄存器 VM，并与 ECS 组件物理咬合

新系统的运行时状态应尽量收敛为最小值类型集合：

- 指令指针；
- 挂起计数 / 等待状态；
- 寄存器数组；
- 少量必要上下文索引。

更关键的是，这份 RAM 不能悬空存在。它必须被打包为纯值类型的 ECS 组件（如 `ExecutionContextComponent`），直接挂载到释放者、子弹或其他承载执行实例的实体上。只有这样，VM 状态、ECS 实体状态与宿主的帧同步 / 回滚框架才能在物理层咬合，快照与恢复才能真正退化为连续内存拷贝。

这意味着：

- 要尽量避免宿主语言对象图携带脚本状态；
- 要避免深层堆对象；
- 要避免运行期分配；
- 要让快照 / 回滚尽量退化为内存拷贝；
- 要让 VM 的 RAM 与 ECS 组件布局直接对齐，而不是通过额外包装层间接转存。

这也是为什么文档多次强调：

- 静态脚本资产是 **ROM**；
- 实例运行状态是 **RAM**；
- RAM 必须作为实体上的纯值类型 ECS 组件存在；
- ROM / RAM 二者必须物理分离。

---

### 2.5 语言层要尽量自然，UI 必须采用基于 `await` 的视图驱动投影

语言设计不能为了可视化而退化成一套难写的节点描述语言。

更合理的方向是：

- 作者先用自然方式写脚本；
- 编译器自动分析 AST；
- 包含 `await`（或位于挂起传播链上）的函数，在主视图中自动展开为结构化流程；
- 不包含挂起语义的纯逻辑块，默认折叠为黑盒节点；
- `[Flow]` / `[Logic]` 仅作为强制覆盖默认行为的兜底标记，而不应成为作者的默认写作负担。

原则上应该优先保证：

- 好写；
- 直觉；
- 不啰嗦；
- 不因适配 UI 而扭曲业务表达。

---

### 2.6 旧系统中沉淀出的“统一效果执行器”思想应被保留

从技能、子弹到状态效果，文档里一个非常稳定的事实是：

- 技能生效点；
- 子弹命中；
- Buff 内部派生伤害 / 加效果；

最终都在不同层面上复用了统一效果执行器思想。

因此，新系统不是要把效果执行完全打散，而是应继续保留这种内核共性：

> 统一的效果执行能力 + 更高层、更清晰的脚本流程调度

这样既能保留战斗业务中已被验证的稳定流水，也能解决旧系统“主流程散落在宿主语言壳层里”的问题。

---

## 三、工程化需求清单 / 设计约束列表

以下内容可直接视为后续脚本、编译器、VM、编辑器设计时的约束基线。

---

### 3.1 业务覆盖层

#### 3.1.1 业务覆盖硬需求

1. 必须统一承载以下三类业务：
   - 技能主流程；
   - 子弹持续行为；
   - 状态效果的附着与事件驱动逻辑。

2. 必须能表达以下控制语义：
   - 顺序执行；
   - 分支；
   - 循环；
   - 函数调用与返回；
   - 提前退出；
   - 中断；
   - 生命周期入口；
   - 等待与恢复；
   - 阶段推进；
   - 事件触发。

3. 必须能覆盖以下战斗语义：
   - 条件判断；
   - 目标筛选；
   - 数据效果；
   - 表现效果；
   - 角色 / 子弹 / Buff 间互相调用；
   - 技能开始 / 结束 / 打断附加逻辑。

#### 3.1.2 业务覆盖设计约束

- 不能只优化线性平铺效果链；
- 复杂分支支持必须是显式硬需求；
- 不能把长期需要 `wait` 的逻辑继续拆散到多个外层对象与管理器中。

---

### 3.2 语言层

#### 3.2.1 语言层硬需求

1. 脚本文本必须是唯一真理源。
2. 语言必须支持自然的函数式 / 过程式表达。
3. 必须原生支持 `wait / await`。
4. 必须支持自定义类型，至少支持结构体。
5. 必须支持脚本间函数调用与返回值。
6. 必须支持局部逻辑、短路表达、局部计算。
7. 必须允许宿主函数通过统一调用表被接入。
8. 必须提供跨生命周期的状态清理机制，例如 `defer` 语句、隐式 `Cleanup` 代码块或等价语义；当 VM 被外力强制中断或销毁前，已注册的清理逻辑必须得到执行，以防止黑板、表现层或宿主状态泄漏。

#### 3.2.2 语言层设计约束

- 不应为了图形化而把语言强行收缩成行为树节点语义；
- 不应为了“结构 / 逻辑分离”而强迫作者做过度拆分；
- UI 必须采用视图驱动模型：编译器自动分析 AST，包含 `await`（或其传播链）的函数自动在主视图展开；不包含挂起语义的纯逻辑块默认折叠为黑盒节点；
- `[Flow]` / `[Logic]` 仅作为强制覆盖默认行为的兜底标记，而不是作者日常书写的默认负担；
- 结构体在语言层可见，但在底层必须被拍扁为连续寄存器槽位；
- 不应依赖运行时对象分配来表达脚本值。

#### 3.2.3 编译器要求

- 编译器应自动分析变量生命周期；
- 跨 `await` 变量提升到持久寄存器；
- 非跨 `await` 局部可使用临时寄存器复用；
- 需要支持调试符号、源码映射、作用域信息保留；
- 前端语法需可替换，但 AST / 语义模型应尽量稳定。

---

### 3.3 VM 执行层

#### 3.3.1 VM 执行层硬需求

1. VM 应采用寄存器式执行模型。
2. VM 的实例运行状态（RAM）必须被打包为纯值类型 ECS 组件，直接挂载到释放者、子弹或其他执行实体上；该组件至少包含：
   - `IP`
   - `WaitCounter / WaitFrames`
   - `Registers[]`
   - 少量必要上下文索引
3. VM 寄存器严禁分配和持有动态数组、托管对象引用或其他不可定长的运行时结构。
4. 脚本层坚持单体逻辑（AoS）表达；涉及多目标的横向批处理必须通过 Syscall 移交 C# 宿主执行，所有临时复杂数据结构只能以整数句柄（`Int Handle`）形式在 VM 中流转。
5. 战斗中严禁运行时 GC 分配。
6. 必须支持状态整体保存与恢复。
7. 快照 / 回滚必须尽量接近 `memcpy` 级成本。
8. 字节码必须在编译期静态生成，跳转地址通过回填确定。
9. 宿主能力必须通过统一 Syscall Table 暴露。
10. VM 必须提供强制中断前的清理执行机制；当实例被外力 Kill / 销毁时，已注册的 `defer` / `Cleanup` 逻辑必须先于上下文回收执行。

#### 3.3.2 VM 执行层设计约束

- 挂起不能依赖宿主协程；
- 挂起不能依赖行为树 `Running`；
- 尽量避免无界调用栈；
- 可接受有限深度调用栈、编译期内联、或对无挂起纯逻辑走宿主快速调用；
- 静态脚本资产与实例运行状态必须物理分离；
- RAM 与宿主 ECS 的组件布局必须直接咬合，避免在回滚链路中出现额外包装层或对象级中转；
- 句柄化临时数据与宿主批处理 Syscall 不是优化建议，而是寄存器定长、零 GC 与快速快照成立的硬性前提；
- 需要时可通过黑板 / 句柄机制与 ECS 或表现层系统交换动态数据；
- VM 的设计应优先服务快照、回滚、一致性，而不是追求图灵完备的通用性幻觉。

---

### 3.4 UI / 编辑器层

#### 3.4.1 UI / 编辑器硬需求

1. 主视图必须是结构化流程图。
2. 必须支持阶段 / 时间轴辅助视图。
3. 必须支持黑盒逻辑节点折叠。
4. 必须支持调试器集成：
   - 断点；
   - 单步；
   - 当前执行位置高亮；
   - 变量 / 寄存器查看；
   - 快照 / 回滚观察。
5. 必须支持源码与流程图双向定位。

#### 3.4.2 UI / 编辑器设计约束

- UI 的责任是提炼流程语义，而不是机械复制源码；
- 主视图只应突出：
  - 入口 / 出口；
  - 等待点；
  - 主要分支；
  - 阶段边界；
  - 调用与副作用节点；
  - 当前执行位置；
- 普通局部计算、公式、细碎表达式不应在主视图大面积展开；
- 局部蓝图式展开只能作为逃生舱，而不能反过来成为主 authoring 模型。

---

### 3.5 性能、同步与状态一致性层

#### 3.5.1 性能与状态一致性硬需求

1. 宿主语言 + VM 的综合效率必须不低于纯 Lua 封闭逻辑方案。
2. 战斗期必须零 GC。
3. 必须天然适配帧同步、预测与回滚。
4. 实例状态必须易于复制、恢复、比较与序列化。
5. 必须严格区分静态数据与实例数据，防止污染。

#### 3.5.2 性能与状态一致性设计约束

- 不能让对象树深拷贝成为回滚成本来源；
- 不能把大量临时状态留在宿主对象图中；
- 不能让编辑器便利性破坏底层状态可控性；
- 必须优先选择值类型、连续内存、预分配结构。

---

### 3.6 演进与迁移层

#### 3.6.1 演进与迁移硬需求

1. 新系统必须支持渐进替换旧系统。
2. 必须允许旧系统与新 VM 在一段时期内共存。
3. 必须允许未来替换语法前端，而不推翻 VM 核心。
4. 宿主交互层应尽量平台中立、引擎中立。

#### 3.6.2 演进与迁移设计约束

- 不应要求一次性全量重写技能 / 子弹 / Buff；
- 不应把核心价值绑定在某一套狭窄 DSL 语法上；
- 应优先稳定 AST、字节码、快照格式、调试接口这些真正长期有效的内核；
- 旧资源向新脚本的转换应尽量可半自动辅助。

---

## 四、明确排除项

以下方向不应成为主方案：

1. **行为树作为总执行模型**
   - 可局部借鉴，但不应成为技能 VM 主语义。

2. **纯蓝图作为唯一 authoring 形式**
   - 可做局部展开与调试，但不应成为唯一真理源。

3. **宿主协程 / 宿主调用栈承载脚本挂起状态**
   - 这会直接破坏快照、回滚与可控性目标。

4. **继续在旧对象系统上叠加补丁规则**
   - 这只能延后问题，不能统一模型。

5. **为了编辑器好画而牺牲语言自然表达**
   - UI 应适应语言语义，而不是反过来绑架语言。

---

## 五、建议作为团队共识保留的一句话

> 新的胶水执行器 / 技能 VM，不是从零凭空发明一套语言，而是把技能、子弹、状态效果三套旧系统中已经客观存在、但目前分散在 C# 对象与资源拼装里的流程语义，统一抬升到脚本层，并用“脚本文本为真理源 + 结构化流程图为主 UI + 寄存器式 VM 为底层 + `wait` 为一等语义 + 零分配快照回滚”为核心约束，构建一套真正适合战斗业务的统一执行架构。

---

## 六、建议的后续推进顺序

如果以工程落地为目标，后续讨论最好按下面顺序收敛：

1. **补齐业务样例集**
   - 尽可能多地列技能、子弹、Buff 的真实复杂案例；
   - 包括等待、命中、打断、事件反应、阶段切换、嵌套调用等。

2. **用样例反推语义最小集**
   - 确认语言必须拥有的控制语义、生命周期入口与调用边界。

3. **确定语言前端策略**
   - 明确 `[Flow] / [Logic]` 是否保留、默认行为如何、UI 自动折叠边界如何判定。

4. **确定 VM 核心状态模型与指令集方向**
   - 包括寄存器布局、挂起指令、调用方式、系统调用表、快照格式。

5. **确定编辑器投影规则**
   - 明确哪些语义进入主流程图、哪些进入时间轴、哪些降级为黑盒节点。

6. **制定渐进迁移方案**
   - 先从哪类技能 / 子弹 / Buff 开始试点；
   - 如何与旧系统共存；
   - 如何验证性能、回滚、调试体验。

---

## 最终压缩结论

这轮讨论已经基本把方向收敛清楚：

- **不是行为树；**
- **不是纯蓝图；**
- **不是继续补旧对象系统；**
- **而是以脚本为真理源、以结构化流程图为主视图、以寄存器 VM 为底层、以 `wait` 为核心语义、以零分配快照回滚为硬约束，去统一技能 / 子弹 / 状态效果三类战斗逻辑。**

这应被视为后续所有脚本设计、编译器设计、VM 设计与编辑器设计的总前提。
