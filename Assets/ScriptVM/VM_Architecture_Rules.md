# VM Architecture Rules

> 本文件不是愿景说明，而是后续所有脚本、AST、编译器、VM、编辑器设计时必须遵守的硬性架构纪律。任何新设计、新语法、新 AST 节点、新 Syscall 提案，只要违反以下任意一条，必须立刻报错并拒绝进入实现。

---

## 1. 真理源与投影规则

1. **脚本文本是唯一真理源。**
   - UI、流程图、时间轴、黑盒节点都只是投影，不是主数据源。

2. **UI 必须采用基于 `await` 的视图驱动模型。**
   - 编译器自动分析 AST；
   - 包含 `await` 或位于挂起传播链上的函数，默认在主视图展开；
   - 不包含挂起语义的纯逻辑块，默认折叠为黑盒节点；
   - `[Flow]` / `[Logic]` 仅作为覆盖默认行为的兜底标记，而不是默认写作负担。

---

## 2. VM 状态与内存纪律

3. **VM 必须是偏瞬态、寄存器式执行模型。**
   - 实例运行状态只能由显式值类型状态构成，例如 `IP`、`WaitCounter / WaitFrames`、`Registers[]` 与少量必要索引。

4. **VM 的 RAM 必须直接映射为 ECS 纯值类型组件。**
   - 运行时状态必须被打包为类似 `ExecutionContextComponent` 的纯值类型 ECS 组件；
   - 该组件直接挂载到释放者、子弹或其他执行实体上；
   - 这是快照 / 回滚可退化为 `memcpy` 的物理前提。

5. **静态脚本资产（ROM）与实例运行状态（RAM）必须物理分离。**
   - 字节码、常量表、调试信息属于静态只读资产；
   - `IP / Wait / Registers` 属于实例 RAM；
   - 二者不得混存，不得让脚本状态残留在宿主对象图中。

6. **VM 寄存器严禁持有动态数组、托管对象引用或不可定长结构。**
   - 任何 AST / 语法 / VM 设计，只要需要让寄存器直接装载动态列表、对象引用、闭包环境或其他不可定长数据，一律判定为违规。

---

## 3. 宿主交互与句柄化纪律

7. **脚本层坚持单体逻辑（AoS）表达。**
   - 脚本描述单体业务流程；
   - 不在脚本层直接承担横向批处理的数据结构管理。

8. **多目标横向批处理必须下放给宿主 Syscall。**
   - AOE、批量筛敌、批量结算、批量碰撞等横向操作，必须通过 C# 宿主执行；
   - VM 只负责任务编排和下达调用，不直接持有批量数据结构。

9. **所有复杂临时数据结构必须句柄化。**
   - 目标列表、距离数组、筛选结果、批处理上下文等复杂临时数据，只能由宿主分配和管理；
   - VM 内部只能流转整数句柄（`Int Handle`）；
   - “句柄化 + 宿主批处理”不是优化建议，而是寄存器定长、零 GC、快速快照成立的硬约束。

10. **宿主能力必须通过统一 Syscall Table 暴露。**
   - 脚本与引擎交互只能通过显式 Syscall 边界完成；
   - 不允许脚本执行状态隐式依赖宿主调用栈、宿主对象成员或隐藏回调约定。

---

## 4. 挂起、回滚与生命周期纪律

11. **`wait / await` 是一等执行语义。**
   - 挂起必须被压缩为显式状态；
   - 禁止依赖宿主协程、行为树 `Running` 或对象树残留状态承载挂起。

12. **快照 / 回滚必须优先于表达便利性。**
   - 任何新能力只要破坏了“状态可整体保存 / 恢复 / 拷贝”的前提，就必须被否决或改造。

13. **必须提供强制中断前的 Cleanup 机制。**
   - 偏瞬态 VM 没有对象析构函数；
   - 因此必须存在 `defer`、`Cleanup` 代码块或等价语义；
   - 当 VM 被外力强制 Kill / 销毁前，已注册的清理逻辑必须先执行，再回收上下文；
   - 否则黑板状态、表现层状态或宿主侧临时状态泄漏，一律视为架构违规。

---

## 5. 语法、AST 与编译器纪律

14. **语法设计必须服从 VM 物理法则，而不是反过来。**
   - 不先假设“高级语言怎么写最舒服”；
   - 先问“这能否映射到定长寄存器、纯值类型状态与明确 Syscall 边界”。

15. **AST 设计必须避免悬空高级结构。**
   - AST 可以表达流程、分支、等待、调用、局部逻辑；
   - 但不能引入无法稳定落到字节码 / 寄存器模型中的抽象。

16. **任何新增业务表达都必须过物理约束校验。**
   - 如果某个业务需求推动出新的 AST / 语法提案，必须先检查：
     - 是否破坏寄存器定长；
     - 是否引入托管分配；
     - 是否绕开 Syscall 边界；
     - 是否破坏快照 / 回滚；
     - 是否无法在强制打断时正确清理。
   - 任一项不通过，则该提案必须被打回重做。

---

## 6. 协作与验证纪律

17. **每次新阶段协作都必须重新注入本文件。**
   - 不假设 AI、设计者或后续实现者能记住长线讨论历史；
   - 本文件必须作为每次阶段推进时的前置规则输入。

18. **文档规则必须尽快落地为可运行锚点。**
   - 包括但不限于：
     - `VMSlot` 结构；
     - `ExecutionContextComponent` 布局；
     - 最小 Syscall ABI；
     - 最小 tracer bullet；
     - 0 GC 回归测试；
     - Save / Load 一致性测试；
     - 强制 Kill 触发 Cleanup 的测试。

19. **一切讨论最终以可执行验证为准。**
   - 如果某个提案在文档上看似合理，但在代码里导致 GC、动态结构泄漏、状态不可 memcpy、或 Cleanup 无法成立，则判定为偏离架构宪法。

---

## 最终裁决原则

> 任何新提案，优先问的不是“写起来爽不爽”，而是：
> 1. 它能否放进定长寄存器和 ECS 纯值 RAM？
> 2. 它是否仍然支持零 GC、快照、回滚与强制 Cleanup？
> 3. 它是否仍然保持 Syscall 边界与句柄化纪律？
>
> 只要答案是否定的，该提案就必须被拒绝或重写。
