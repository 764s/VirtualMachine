# FFEditor 胶水执行器与技能虚拟机架构总纲 (第三部)

## 1. 架构最高原则：控制流与数据流的物理隔离 (ROM vs RAM)

在基于 ECS 架构与帧同步回滚的 2D 横版动作游戏中，虚拟机的状态必须绝对可控。为此，系统彻底放弃了传统面向对象脚本中“脚本实例持有自身数据”的模型。

* **静态指令资产 (ROM)：**
    * **设计：** 编译后的脚本是一份纯粹的静态数据（Bytecode 指令流、常量表、最大寄存器需求量）。在内存中，同一种技能无论有多少个释放者，永远只存在一份只读 ROM。
    * **推演：** 虚拟机必须是“无状态的函数执行器”。只有将逻辑彻底固化为只读指令，才能保证在任意时刻热更代码而不破坏当前战斗状态。
* **动态执行上下文 (RAM)：**
    * **设计：** 真正的状态（Instruction Pointer, WaitFrames, 临时寄存器数组）被剥离出来，作为纯值类型组件（`ExecutionContextComponent`）挂载到释放技能的 ECS 实体上。
    * **推演：** 这种设计使得网络回滚或快照保存退化为极其廉价的内存拷贝（Memcpy）。实体的状态数据可以紧密打包在 ECS 的连续内存块中，完美契合 CPU 缓存。

## 2. 软硬件分工：纵向脚本书写与横向系统调用

在 ECS 架构下，为了兼顾开发者书写直觉（DX）与底层横向批处理（SoA）的狂暴性能，必须对“脚本能做什么”设定严格的物理边界。

* **脚本层：坚持纵向标量设计 (AoS 视角)**
    * **设计：** 语法层面保留原生的 `for`、`if-else` 等嵌套分支结构，作者以处理单一实体的直觉来编写逻辑。
    * **推演：** 尝试在脚本编译器中实现“自动矢量化（If-Conversion）”成本过高且容易引发副作用地雷。保留纵向标量书写，可以让极其复杂的单体特判（如 Boss 弱点结算、霸体/防御状态分支）写起来符合人类直觉。
* **宿主层：提供横向批处理系统调用 (Batch Syscalls)**
    * **设计：** 面对 AOE 或大规模目标筛选，脚本不再使用 `for` 循环遍历，而是调用 `Syscall_BatchApplyDamage(groupHandle)` 等批处理接口。
    * **推演：** 将计算密集型的横向内存刷写任务踢回给最擅长此道的 C# ECS 底层。虚拟机（VM）扮演指挥官，只负责下达指令；宿主引擎扮演执行部队，负责高效遍历。
* **临时数据的句柄化管理 (Handle-Based Transient Data)**
    * **设计：** 虚拟机内部的寄存器**绝对不允许**分配和持有动态数组。横向处理产生的所有临时数据（如目标列表、距离数组）均由宿主 C# 侧的“帧级作用域内存池（Bump Allocator）”分配，并仅向 VM 返回一个整数句柄（Int Handle）。
    * **推演：** 保证了 VM 寄存器大小的绝对恒定。每帧结束时，宿主侧瞬间重置内存池游标，实现大规模计算的真正零 GC。

## 3. 内存容器革命：动态插槽与定长物理存储

编译器分析出的局部变量数量是动态多变的，但 ECS 要求内存大小绝对固定。

* **类型擦除联合体 (The `VMSlot` Union)：**
    * **设计：** 在 C# 底层使用 `[StructLayout(LayoutKind.Explicit)]`，将 `int`、`float`、`bool` 和 `handle` 强制塞入同一个 32 位（或 64 位）的物理插槽中。
    * **推演：** 抹平了脚本中的类型差异，使寄存器数组变成极其纯粹、易于拷贝的内存块。
* **静态定长暴力美学：**
    * **设计：** 无论脚本实际需要几个局部变量，宿主在初始化实体组件时，统一预分配固定数量的插槽（如 `fixed VMSlot Registers[32]`）。
    * **推演：** 放弃一部分内存利用率（Padding 浪费），换取绝对的内存连续性和防止堆分配（Capacity 溢出）。若编译期发现变量需求超出上限，直接报错拒绝。

## 4. 跨界数据通信：黑板模式 (Blackboard Pattern)

如何让通用的、预定义的 ECS 实体，与随心所欲声明 `public` 变量的动态脚本完美咬合？

* **“黑板”作为通用数据总线：**
    * **设计：** ECS 实体不预定义具体的业务字段（如 `ChargeLevel`），而是挂载一个仅包含“Hash-Value”键值对的通用定长数组组件（`BlackboardComponent`）。
    * **推演：** 彻底解耦。宿主实体无需因为脚本增加新变量而重新编译结构体，它只是提供“空白格子”的无情打工人。
* **字符串的编译期 Hash 降级：**
    * **设计：** 脚本中声明的 `public float MagicPower`，在编译期被转化为 `Syscall_SetBlackboard(EntityId, Hash("MagicPower"), value)`，彻底消灭运行时字符串。
    * **推演：** 外部的 UI、特效或状态机系统，通过向黑板查询对应的 Hash ID 来获取表现层数据。维持了底层引擎的纯粹值类型特性，同时赋予了表现层极大的动态灵活性。

## 5. 控制流边界：受限的调用栈与编译期魔法

为了保证快照回滚的极致性能，必须打破图灵完备语言的“无限调用栈”设定。

* **定长调用栈 (Bounded Call Stack)：**
    * **设计：** 在实体的执行上下文中，硬编码固定深度的调用栈帧数组（例如最大深度为 4 层）。
    * **推演：** 动态堆栈是帧同步的一生之敌。对于动作游戏的战斗主流程而言，4 层的挂起深度已完全溢出业务需求。
* **编译期内联与纯逻辑委托：**
    * **设计：** 脚本编译器在处理 `[Flow]` 互相调用时，尽可能采用内联展开（AST Inlining）将其拍扁为一维指令；对于无 `await` 的 `[Logic]` 调用，VM 不进行压栈，而是通过 Syscall 委托给 C# 原生调用栈瞬间算完并返回。
    * **推演：** 这种底层限制被编译器的魔法完美掩盖。开发者在 UI 连线或文本书写时，依然感觉拥有无限嵌套的拆分自由，实现了极佳的开发者体验（DX）。
